4. Планы по расширению производственных мощностей после сделки.

✍️ ЧЕРНОВИК ПОСТА
На рынке жидкостного охлаждения обсуждают технику: расход, дельту температур, тип фитингов. Реже обсуждают, кто владеет цепочкой от теплоносителя до cold plate. Ecolab закрыла покупку CoolIT Systems. Это соединяет поставщика химии для тепловых контуров и одного из ключевых производителей CDU и cold plates для ЦОД.

Для интегратора это означает две вещи. Первое: спецификация теплоносителя перестаёт быть нейтральным пунктом BOM. Вендор оборудования теперь заинтересован в том, чтобы в контуре циркулировала жидкость его же группы. Второе: матрица совместимости «жидкость — cold plate — материалы уплотнений» становится инструментом сегментации рынка. Разные производители пойдут по этому пути с задержкой в 12–18 месяцев.

Отсюда вопрос к тем, кто проектирует контур охлаждения на 7–10 лет вперёд: закладываете ли вы в контракт независимость выбора теплоносителя, или соглашаетесь на связанную поставку ради упрощения гарантии?

🔹 ТЕМА 3/4 · GPU-ШЕРИНГ ЧЕРЕЗ СЕТЬ
Gleam: адаптивный CUDA API remoting для совместного использования GPU по LAN

📌 ФАКТ
Опубликована работа Gleam, описывающая адаптивный сетевой протокол CUDA API remoting для разделения GPU между устройствами в локальной сети (arXiv 2607.23115, 28 июля 2026). Цель — совместное использование GPU-ресурсов гетерогенных устройств для AI inference.

📍 КОНТЕКСТ
Классические подходы к разделению GPU — MIG на уровне драйвера и виртуализация через vGPU. Оба привязаны к физической машине. Сетевой remoting возвращает старую идею rCUDA в новом виде, ориентируясь на inference edge-устройств.

🎯 РЕЛЕВАНТНОСТЬ ДЛЯ AI DISTRIBUTION PLATFORM
Низкая. Исследовательский уровень зрелости, промышленных внедрений не описано. Стоит держать в поле зрения графа совместимости для сценариев edge-inference.

🔮 ПРОГНОЗ НА 12 МЕСЯЦЕВ
→ Низкий: работа остаётся академической, отраслевого внедрения нет. Механизм — типовая судьба ресерч-проектов без индустриального спонсора.
→ Базовый: подход применяется в узких edge-сценариях (розница, промышленный IoT) через open-source реализации. Актор — интеграторы edge-решений с ограниченным бюджетом GPU.
→ Высокий: NVIDIA включает аналогичный механизм в референс-стек NIM или Jetson SDK как альтернативу MIG для распределённого inference. Причина — рост нагрузок edge-inference и запрос на совместное использование GPU между несколькими устройствами.

❓ ОТКРЫТЫЕ ВОПРОСЫ
1. Задержка сетевого вызова CUDA API относительно локального вызова — конкретные цифры в переданной аннотации не указаны.
2. Поведение при потере пакетов и отказе сети во время выполнения kernel.
3. Совместимость с современными версиями CUDA runtime и cuDNN.
4. Модель безопасности при разделении GPU между недоверенными клиентами.

✍️ ЧЕРНОВИК ПОСТА
Разделение GPU обычно обсуждают на уровне одной машины: MIG, vGPU, time-slicing. Работа Gleam возвращает старый вопрос: можно ли разделять GPU между устройствами по локальной сети через remoting CUDA API. Идея не новая (rCUDA существует более десяти лет), но контекст изменился.

Раньше сетевой remoting проигрывал из-за задержек, а рабочие нагрузки были тренировкой с большим объёмом обмена. Сейчас доминирующая нагрузка edge — inference с короткими вызовами и малыми батчами. Здесь сетевой overhead становится приемлемым, а разделение одного GPU между несколькими устройствами даёт экономический эффект.

Практический вопрос не в том, работает ли протокол, а в том, кто возьмёт на себя операционную ответственность за сетевой контур GPU: интегратор, платформенный провайдер или заказчик. Именно здесь академические работы обычно останавливаются, а промышленные внедрения буксуют.

Кто уже пробовал разделять GPU по сети в production edge-сценариях и с какими отказами столкнулся?

🔹 ТЕМА 4/4 · AI BUSINESS APPLICATIONS
Persistent verified memory: замороженная модель 12B с ростом точности через накопление решений

📌 ФАКТ
Опубликована работа «A Frozen 12B Beats Frontier Models on Verified Work: 100% Accuracy, 0 Tokens, Bit-Exact, Forever» (HuggingFace Daily Papers, автор Sietse Schelpe, 28 июля 2026). Подход: модель остаётся неизменной, рядом растёт persistent memory верифицированных решений; после первого решения задачи с независимой верификацией все последующие экземпляры того же класса задач возвращаются из памяти детерминистически.

📍 КОНТЕКСТ
Доминирующая парадигма улучшения модели — retraining или fine-tuning с высокой стоимостью compute и непредсказуемым результатом. Альтернативный путь — retrieval-augmented generation и caching, но без формальной верификации ответа. Подход в статье вводит промежуточный слой: верификатор, независимый от ответа модели, и persistent-хранилище проверенных решений.

🎯 РЕЛЕВАНТНОСТЬ ДЛЯ AI DISTRIBUTION PLATFORM
Высокая. Влияет на TCO-калькулятор и BOM-генератор для inference-конфигураций: смещает баланс от «больше GPU для frontier-моделей» к «средняя модель плюс verified memory store».

🔮 ПРОГНОЗ НА 12 МЕСЯЦЕВ
→ Низкий: подход остаётся исследовательским, промышленных фреймворков не появляется. Механизм — отсутствие стандартного верификатора для доменов вне математики и кодогенерации.
→ Базовый: два-три вендора инструментов (Anthropic, Weights & Biases, LangChain) выпускают SDK для persistent verified memory в узких доменах: SQL-запросы, юридические классификаторы, финансовая отчётность. Актор — вендоры MLOps с интересом к снижению стоимости inference.
→ Высокий: enterprise-заказчики начинают требовать persistent verified memory как замену fine-tuning для регулируемых доменов (банки, здравоохранение), где нужна детерминистическая воспроизводимость. Причина — регуляторный запрос ЕС AI Act на аудируемость ответов модели.

❓ ОТКРЫТЫЕ ВОПРОСЫ
1. Как определяется «класс задачи» для сопоставления с записью в persistent memory — точные критерии эквивалентности не раскрыты в аннотации.
2. Стоимость и требования к инфраструктуре верификатора для доменов вне формальной верификации (математика, код).
3. Устойчивость подхода к drift в входных данных: что происходит, когда формулировка задачи слегка меняется.
4. Как persistent memory масштабируется до миллионов записей без деградации retrieval.

📋 BACKLOG-ITEM (Этап 3b)
Название: Добавить в TCO-калькулятор сценарий «средняя модель + persistent verified memory» как альтернативу frontier-инференсу
Триггер: публикация работы Sietse Schelpe о persistent verified memory для замороженной 12B-модели (arXiv/HuggingFace Daily Papers, 28 июля 2026)
Затронутые компоненты: TCO-калькулятор, BOM-генератор
Требования:
  1. Ввести в TCO-модель параметр «доля запросов, обслуживаемых из verified memory» с диапазоном 0–95% — от него зависит требуемый GPU-парк, и без этого параметра расчёт inference-стоимости не отражает актуальные архитектуры.
  2. Добавить в BOM отдельную позицию под persistent memory store (SSD NVMe, метаданные, верификатор) — без выделенной позиции подсистема пропадает в общей смете и её TCO не считается.
  3. Ввести в граф совместимости класс «verifier» и его привязку к домену задачи — без этого невозможно оценить применимость подхода для конкретного клиента.
  4. Добавить в документацию раздел с ограничениями подхода (domain-specific verifier, drift, cold start) — интегратор должен видеть границы применимости до продажи.
Приоритет: P1 (в ближайший квартал)
Открытые вопросы блокирующие реализацию: пункты 1 и 2 из ❓ ОТКРЫТЫЕ ВОПРОСЫ — до их закрытия TCO-модель работает на допущениях автора платформы, не на верифицированных данных.

✍️ ЧЕРНОВИК ПОСТА
Стандартный способ улучшить LLM — переобучить её. Дорого, непрозрачно, каждый цикл даёт новую модель с новым поведением. Работа Sietse Schelpe предлагает другой путь: модель заморожена, рядом растёт persistent memory верифицированных решений. Первый экземпляр задачи решается моделью и проходит независимую верификацию. Все последующие экземпляры того же класса возвращаются из памяти детерминистически.

Для инженерной оценки важны два ограничения. Первое: подход опирается на существование независимого верификатора. В математике и кодогенерации он есть (доказательство, компилятор, тесты). В классификации юридических документов или медицинских записей — нет готового верификатора, его нужно строить отдельно, и его стоимость может превышать экономию на inference.

Второе: определение «класса задачи» — критическая точка. Слишком узкое определение убивает попадание в кэш, слишком широкое возвращает неверные решения.

Для TCO это меняет расчёт: параметр «доля запросов из verified memory» становится главным рычагом стоимости inference, важнее выбора GPU.
